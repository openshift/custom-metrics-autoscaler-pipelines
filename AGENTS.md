# AGENTS.md — openshift/custom-metrics-autoscaler-pipelines

This file provides AI-specific guidance for working in the Custom Metrics Autoscaler pipelines repository. For contribution guidelines, see [CONTRIBUTING.md](CONTRIBUTING.md).

## Project Overview

This is the **build and release pipeline repository** for Custom Metrics Autoscaler (CMA) for OpenShift. It does not contain Go source code. Instead, it uses git submodules to pull source from the component repos and defines the Dockerfiles, Tekton pipelines, operator bundle assembly scripts, and OLM File-Based Catalogs (FBC) needed to build and release all CMA container images via [Konflux](https://konflux-ci.dev/).

The CMA product consists of images built from three source repos:
- [openshift/kedacore-keda](https://github.com/openshift/kedacore-keda) — KEDA controller, metrics adapter, and admission webhooks
- [openshift/custom-metrics-autoscaler-operator](https://github.com/openshift/custom-metrics-autoscaler-operator) — CMA operator and operator bundle (CSV)
- [openshift/kedacore-http-add-on](https://github.com/openshift/kedacore-http-add-on) — HTTP Add-on interceptor, operator, and scaler

## Repository Structure

```
Dockerfile.*                    # One Dockerfile per container image (8 total + 1 bundle)
.tekton/
  multi-arch-build-pipeline.yaml  # Shared pipeline for multi-arch builds
  single-arch-build-pipeline.yaml # Shared pipeline for single-arch (FBC) builds
  *-pull-request.yaml             # Per-component PR trigger PipelineRuns
  *-push.yaml                     # Per-component push trigger PipelineRuns
bundle-hack/
  update_bundle.sh              # Assembles the operator bundle CSV with image pullspecs
  regen-fbc-catalog.sh          # Renders FBC catalogs from templates using opm
  new-release.sh                # Adds a new release entry to the FBC template
  imagerefs/                    # Image pullspec reference files (updated by Konflux nudges)
  imageref_test.sh              # Tests for imageref validity
catalogs/
  fbc/                          # Production FBC catalog templates and rendered catalogs
  fbc-stage/                    # Staging FBC catalog templates and rendered catalogs
  */catalog-template.yaml       # FBC template (input to opm alpha render-template)
  */catalog/                    # Rendered catalog output (generated, do not hand-edit)
hack/
  update_generic_deps.sh        # Updates artifacts.lock.yaml with latest OCP client + protoc
repos/                          # Renovate-managed RPM repo files for lockfile refresh
tools/                          # Git submodules for build tools (mockgen, controller-tools, protobuf)
kedacore-keda/                  # Git submodule: KEDA source
custom-metrics-autoscaler-operator/  # Git submodule: CMA operator source
kedacore-http-add-on/           # Git submodule: HTTP Add-on source
releaseNum                      # Current release number (appended to CSV version)
build-bump                      # Trigger file: any update triggers all non-catalog builds
rpms.in.yaml                    # RPM dependency input for Konflux lockfile generation
rpms.lock.yaml                  # Generated RPM lockfile (do not hand-edit)
artifacts.lock.yaml             # Lockfile for non-RPM build artifacts (OCP client, protoc)
renovate.json                   # Renovate config for automated RPM lockfile refresh
OWNERS                          # Prow approver list
```

## Common Pitfalls

1. **Do not hand-edit rendered FBC catalogs.** The files under `catalogs/*/catalog/` are generated by `bundle-hack/regen-fbc-catalog.sh` from `catalog-template.yaml`. Edit the template, then regenerate.

2. **Do not hand-edit `rpms.lock.yaml`.** This file is generated by Konflux from `rpms.in.yaml` and managed by Renovate. Changes will be overwritten.

3. **Image pullspec files are managed by Konflux nudges.** The `.pullspec` files in `bundle-hack/imagerefs/` are automatically updated when upstream component images are rebuilt. Manual edits are rarely needed and will be overwritten by the next nudge.

4. **Version changes touch many files.** A new semver release requires updates to `ARG CMA_VERSION` in 7 Dockerfiles, `LABEL version` in the bundle Dockerfile, `cpe=` labels in all 8 Dockerfiles, the `releaseNum` file, and the FBC catalog templates. See the [Release Version Bump Checklist](#release-version-bump-checklist) below.

5. **`on-cel-expression` filters control what gets built.** Each component's `.tekton/*-pull-request.yaml` has a CEL expression that limits builds to relevant file changes. If you add a new file that should trigger a build, update the CEL expression.

6. **Submodules must be initialized.** After cloning, run `git submodule update --init` to populate the source submodules. Builds will fail without them.

7. **The bundle script rewrites image pullspecs for the target registry.** `bundle-hack/update_bundle.sh` rewrites pullspecs from the Konflux build registry to the production or staging registry. Changes to this rewriting logic can break disconnected installs if `relatedImages` is wrong.

8. **`build-bump` is a trigger file.** Any commit that touches `build-bump` triggers rebuilds of all non-catalog components. Use it to force a full rebuild (e.g., after a base image update).

## Architecture: What Is Not Obvious

### Build Flow

1. Source code lives in git submodules (`kedacore-keda`, `custom-metrics-autoscaler-operator`, `kedacore-http-add-on`)
2. Each Dockerfile copies source from its submodule and builds a container image
3. Konflux Tekton pipelines in `.tekton/` trigger builds on PRs and pushes, using CEL expressions to build only affected components
4. When an operand/operator image is pushed, Konflux "nudges" this repo by opening a PR that updates the image digest in `bundle-hack/imagerefs/*.pullspec`
5. The bundle Dockerfile runs `bundle-hack/update_bundle.sh` during build, which assembles the CSV with the correct image pullspecs and version metadata
6. FBC catalogs reference bundle images and define the OLM upgrade graph; they are regenerated from templates with `bundle-hack/regen-fbc-catalog.sh`

### Two Catalog Variants

- `catalogs/fbc/` — Production catalogs with `registry.redhat.io` pullspecs
- `catalogs/fbc-stage/` — Staging catalogs with `registry.stage.redhat.io` pullspecs (currently rewritten to `registry.redhat.io` with an ICSP redirect)

Each has per-OCP-version Containerfiles (`Containerfile.catalog-4-18`, etc.) and a shared `catalog-template.yaml`.

### Pullspec Rewriting

The bundle and catalog build scripts rewrite image references from the Konflux build registry (`quay.io/redhat-user-workloads/cma-podauto-tenant/...`) to the final delivery registry (`registry.redhat.io/custom-metrics-autoscaler/...`). The rewriting adds an OS version suffix (`-rhel9`) and maps component names to their product image names.

## Human-in-the-Loop Triggers

Stop and consult a human before:

- **Changing bundle assembly logic** (`bundle-hack/update_bundle.sh`) — Errors here produce broken operator bundles with wrong image references
- **Modifying FBC catalog templates** — Incorrect upgrade graph entries can break OLM upgrades for customers
- **Changing shared Tekton pipeline definitions** (`.tekton/multi-arch-build-pipeline.yaml`, `.tekton/single-arch-build-pipeline.yaml`) — These affect builds for all components
- **Modifying Dockerfile base images** — Base image changes affect security scanning, FIPS compliance, and architecture support
- **Version bumps** — See the checklist below; incomplete bumps produce broken releases
- **Adding or removing components** — Requires coordinated changes to Tekton pipelines, Dockerfiles, nudge configuration, and FBC catalogs

## Paired Changes

| If you change... | Also update... |
|-----------------|----------------|
| `ARG CMA_VERSION` in Dockerfiles | All 7 non-bundle Dockerfiles, `LABEL version` in bundle Dockerfile, `cpe=` labels, `releaseNum`, FBC catalog templates |
| `LABEL release` in Dockerfiles | All 8 Dockerfiles and `releaseNum` file |
| FBC `catalog-template.yaml` | Run `bundle-hack/regen-fbc-catalog.sh` to regenerate rendered catalogs |
| `.tekton/*-pull-request.yaml` CEL expressions | Corresponding `*-push.yaml` CEL expressions |
| `rpms.in.yaml` | Regenerate `rpms.lock.yaml` via Konflux |
| A new Dockerfile for a new component | Add `.tekton/` PipelineRuns, pullspec file in `bundle-hack/imagerefs/`, update `bundle-hack/update_bundle.sh` |

## Release Version Bump Checklist

When shipping a new release, version metadata must be updated across multiple files. There are two scenarios:

### New semver (e.g. 2.19.0 -> 2.20.0)

Update **all** of the following:

1. **`ARG CMA_VERSION`** in every Dockerfile (except the bundle, which uses a hardcoded `LABEL version`):
   - `Dockerfile.cma-operator`
   - `Dockerfile.keda-operator`
   - `Dockerfile.keda-adapter`
   - `Dockerfile.keda-webhooks`
   - `Dockerfile.http-addon-operator`
   - `Dockerfile.http-addon-scaler`
   - `Dockerfile.http-addon-interceptor`

2. **`LABEL version`** in `Dockerfile.cma-operator-bundle` (hardcoded, not from ARG)

3. **`cpe=` label** in all 8 Dockerfiles (major.minor only, e.g. `cpe:/a:redhat:openshift_custom_metrics_autoscaler:2.19::el9`)

4. **`LABEL com.redhat.openshift.versions`** in all 8 Dockerfiles if the target OCP version is changing

5. **`LABEL release`** in all 8 Dockerfiles — reset to `"1"` for a new semver

6. **`releaseNum`** file — reset to `1` (this gets appended to the CSV version in the bundle)

7. **FBC catalog templates** — update channel entries in:
   - `catalogs/fbc/catalog-template.yaml`
   - `catalogs/fbc-stage/catalog-template.yaml`

### Same semver, new release (e.g. security rebuild of 2.19.0)

Only increment the release number:

1. **`LABEL release`** in all 8 Dockerfiles — increment (e.g. `"1"` -> `"2"`)
2. **`releaseNum`** file — increment to match
3. **FBC catalog templates** — update channel entries to reference the new `-N` suffix (e.g. `v2.19.0-1` -> `v2.19.0-2`)
